# 任务通知推送与确认闭环（1.1）

## 要解决的问题

1.0 让会议上下文进得了 Agent，但会上拍板的**任务**仍然只存在于纪要文本里，要靠人手动复制粘贴给 Agent，
散落在各会话中——无状态、无归属、无截止。一场会「开了等于没开」。

1.1 把任务变成系统里的持久化实体，作为唯一真相源。本文件说明任务从「纪要完成」到「逐条确认」再到
「状态落库」的完整逻辑，以及每一项设计决策背后的取舍。

## 完整链路

```
纪要生成（本地 Agent 产出 minutes + evidence）
  → 任务抽取：本地 LLM 从纪要提取任务草稿
      每条带：标题、来源会议、建议执行方、会上原话、时间锚点
  → 进「待确认」闸门（不确认永远不进正式清单）
  → 飞书推送卡片：逐条「✅确认 / 驳回」按钮
  → 用户在飞书点按钮
  → 长连接回调收到 card.action 事件
  → 校验操作者 → 任务状态落库（confirmed / cancelled）
  → 卡片原地更新：该条变「已确认」，保留来源/建议/原话，其余条目不动
  → 项目看板同步；执行、登记交付物、标记完成
```

## 数据流与隐私边界

```
纪要/逐字稿（本机）──► 任务抽取（本地 LLM）──► 任务实体（本机 SQLite）
                                                │
                                                ▼
                                    飞书卡片（外发内容仅限）：
                                      任务标题
                                      来源会议名
                                      一段会上原话
                                      确认/驳回按钮
                                                │
                                                ▼
                                    用户点按钮 → 长连接回调回本机
                                    （卡片回调经 WebSocket 推送，无公网端口暴露）
```

要点：

- **外发的只是任务摘要，不是会议全文。** 卡片上只有任务标题、来源会议名与一段原话。
- **回调走长连接，不开放任何公网端口。** 本地进程主动连飞书长连接接收 card.action，
  数据不出本机、不需要公网地址，天然适合本地化部署。
- **会议内容全部留本机。** 转写、逐字稿、纪要、说话人分离、语义索引、任务状态都在本机。

## 关键设计决策

### 1. 任务先进「待确认」闸门

抽取出来的任务一律 `pending_confirm`，不确认永远不进正式清单。会上闲聊里那句「这个是不是也可以考虑一下」
不该变成一条任务——闸门把拍板与闲聊分开，这是防止任务清单被灌满的唯一防线。

### 2. 逐条确认，不做「全部确认」

任务是一条一条的，逐条过一遍才知道每条是什么、要不要。批量确认等于没看，违背确认的本意。
所以卡片上每条任务独立一个「确认/驳回」按钮，不提供批量操作。

### 3. 卡片自包含，不放外链

系统是本地化部署，外部网络访问不到工作台地址。卡片上任何链接都是死路，所以卡片必须自包含：
来源、建议、原话、按钮都在卡上，不依赖跳转。确认后原地更新，之前确认过什么一眼可见。

### 4. 确认后保留全部细节，可追溯

点完确认，那条任务只把按钮换成「已确认」状态，**来源 / 建议 / 原话全部保留**。
确认不是把信息收走，而是给这条任务盖一个「已处理」的章。

### 5. 卡片回调必须由「应用机器人」发送

飞书交互卡片的按钮回调（`card.action.trigger`）是应用级事件：只有**应用机器人**发的卡能收到按钮回调，
纯自定义机器人只能发卡、收不到。所以任务确认卡必须由带回调能力的应用发送，回调事件经
**长连接（WebSocket）** 接收——不需要公网回调地址。

### 6. 幂等与重试

- 同一批任务只推一次卡（通知台账去重）。
- 回调重复点击不重复生效（状态迁移校验 + 幂等）。
- 抽取失败自动重试；任务已被重新抽取覆盖的旧卡，点击时保留原卡细节、不塌缩。

## 卡片消息格式（卡片 2.0）

任务确认卡使用飞书卡片 2.0（`schema: "2.0"`）。要点：

- 每条任务一个灰底信息块：标题、建议、时间点、📌 会上原话。
- 每个信息块下跟一组「✅确认 / 驳回」按钮，按钮 value 携带 `task_id` 与 `extraction_id`。
- 双按钮并排用 `column_set`（卡片 2.0 不支持 `button_group` 与 `action` 容器）。
- 回调事件里 `event.action.value` 携带自定义载荷，`event.context.open_message_id` 指向原卡，
  确认后据此原地更新。

参考实现见 [`task-notify/cards.py`](../task-notify/cards.py) 与
[`task-notify/card_listener.py`](../task-notify/card_listener.py)。

## 前置条件

1. 一个飞书**应用机器人**（不是自定义机器人），并在开放平台开启「回调配置 = 长连接」、
   订阅 `card.action.trigger`。
2. 应用机器人加入要接收任务卡片的群。
3. 本机有飞书 CLI（lark-cli）能访问该应用的凭证。
4. 任务抽取需要本地配置的 LLM（工作台可配置）。

任一条不满足，确认闭环自动降级回工作台网页内完成——转写、归档、任务看板不受影响。

## 与工作台的配合

- 任务看板在 `workbench/` 内：状态流转、项目归属、交付物登记。
- 卡片推送是看板的**出口**：飞书是提醒与确认的入口，看板是任务状态的真相源。
- 纪要重新生成会产生新的抽取批次；旧批次的卡片保留原样，不主动塌缩。

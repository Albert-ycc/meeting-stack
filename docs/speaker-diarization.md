# 说话人分离：把引擎早就产出的数据接进应用

v1.3 的主题不是「加一个说话人分离功能」，而是一次典型的存量能力启用：转写引擎（FunASR + cam++）
从一开始就带着 `spk_model="cam++"` 在跑，每场会的 `*.funasr.json` 里逐句都有说话人编号，磁盘上
的 `*.spk.txt` 也一直在按说话人分组——但工作台的逐字稿里每段都只显示「说话人」三个字。数据库的
说话人字段、前端的展示与改名界面全部就绪，只是从没被数据填过。

断点只有一处：导入器选逐字稿来源时，无说话人的 SRT 排在有说话人的 funasr_json 前面。

这份文档记录修通这条链路时沉淀的设计决策。它们大多不是「说话人分离」特有的，而是任何
「给已上线数据补一个新字段」的场景都会遇到的。

## 先修 bug：切块转写的说话人编号会静默碰撞

长录音（约 50 分钟以上）会被切块分别转写，防止说话人聚类吃爆内存。切块的副作用是：
**每块的说话人编号各自从 0 开始**。转写脚本在人读的产物（`.spk.txt`）里用 `c1-spk0` /
`c2-spk0` 这样的块前缀区分，但机器读的 `.funasr.json` 存的是每块原始输出——裸数字。

解析器如果直接把数字转成 `SPEAKER_00`，两个块里各自的 0 号说话人（完全可能是不同的人）
会得到同一个标签。我们量化过影响：14 场切块长会合计 195 个真实说话人簇，直接解析后只剩
112 个标签——83 个簇被静默并进了别人名下。用户把某个标签改名成真名的那一刻，另外半场会里
另一个人的发言也被冠上了这个名字，而且界面上完全看不出异常。

修法很小：解析时感知块结构，多块时标签带块前缀（`C1_SPEAKER_00`），单块保持原样。
跨块的同号说话人到底是不是同一个人，这是声纹层（embedding 全局聚类）才能回答的问题，
解析层的职责是**保真**，不是**合并**。保真了，后面才有得聚；入库时就抹平，神仙也拆不开。

## 设计决策

**1. 文本权威不换，只补字段。** 最初的方案是把 funasr_json 提到 SRT 前面整体替换来源。
评审推翻了它：坏 json（截断、非法字节、字段缺失）会让整场逐字稿导入失败，而实测两个来源
的文本逐段完全相同（SRT 本来就是同一次转写生成的）。既然文本一致，json 唯一的增量就是
说话人字段——按段序号对齐、逐段校验文本严格相等后，只补 `speaker_label` 一列。坏 json 的
最坏后果从「整场没有逐字稿」降到「这场没有说话人标签」。

**2. 就地 UPDATE，不新建版本。** 「不原地改已有数据」听起来是美德，但新建版本意味着所有
段落换新 id——以段 id 为主键的语义检索向量（近 9 万条）全部静默失效，恢复要加载模型全量
重算。就地补一个此前恒为 NULL 的字段：向量、全文索引、版本链、发布标记全部零影响，
回滚就是 `SET speaker_label = NULL`。判断标准不是「改没改已有行」，而是「改动的血缘
半径有多大」。

**3. 手改判定用确定性信号，不用内容 hash。** 要保护用户手工编辑过的会议不被回填覆盖。
最初设计是重新解析源文件算内容 hash 比对——评审发现两个坑：部分源文件已被清理（hash 算不
出来会误判成手改，白白跳过），而且编辑操作在这套系统里**必然**产生一个草稿版本（这是既有
机制）。所以「有没有草稿版本」一条 SQL 就是精确信号。有确定性标记时，启发式比对只会更差。

**4. 同一件事只留一个实现。** 仓库里有两套 speakers 表同步逻辑：一套「删光重建」，一套
「UPSERT 保留已改的名字」。语义相反，调错一个，幂等重跑会把用户标好的真名全部清掉。回填
固定走 UPSERT，两套实现的收敛单独立项。这是这个代码库第二次栽在双实现漂移上（第一次在
纪要校验），教训通用：跨模块的同一规则，下沉成一个共享函数，别各写一份。

**5. 并发控制靠锁，不靠停服。** 「跑脚本前先停服务」在有进程守护的机器上是幻觉——
launchd 每 5 分钟会把服务拉回来，回填窗口内扫描循环必然复活并发写库。正确做法是复用
扫描器自己的文件锁（fcntl 排它锁）：回填持同一把锁，天然互斥，服务甚至不用停。

**6. 幂等靠事件台账，不靠数据本身。** 「已经有标签就跳过」看似合理，直到下一次 parser
修 bug——修复版永远进不去（数据「已经有了」）。回填每场成功后写一条带脚本版本号的事件，
重跑按事件判断。数据是结果，事件才是账本。

**7. 验收要有独立第二信源。** 「speaker_label 非空计数 > 0」这类验收测不出任何数据错误
（全填同一个值也通过）。真正的验收：每场库内的标签基数，对照转写侧独立生成的 `.spk.txt`
里的标签基数——两条完全独立的链路算出同一个数，才敢说数据是对的。切块碰撞 bug 就是这条
验收直接抓出来的（112 ≠ 195）。

## 评审方式

这次的方案在动手前过了一轮四角色评审（架构 / 后端 / 前端 / 测试），每个角色被强制要求
带「信息差」：必须做方案起草人没做过的取证动作（逐行读真实代码、只读查生产库、读真实
数据文件、构造破坏场景实跑）才准下结论，允许交白卷但必须附取证清单。四路各自独立发现了
切块碰撞这个 P0，且三路推翻了草案的三个核心假设。同一个模型换个角色名再读一遍方案不产生
独立性——独立性来自不同的输入源，不来自不同的人设。

## 局限

- 切块会议里 `C1_SPEAKER_00` 与 `C2_SPEAKER_00` 是否同一人，需要声纹 embedding 跨块
  聚类才能回答，本版不做，标签保真即可。
- 跨会议认人（「这是谁」而不是「第几号说话人」）是独立的声纹识别工程，涉及样本录入、
  阈值校准、影子上线，不在本版范围。
- 单麦克风远场的自动聚类天然「主干可信、边界串段」，改名界面明确只作用于当前标签，
  不承诺跨块、跨会议的身份一致性。

参考实现见 `speaker-diarization/`：`chunk_aware_labels.py`（切块感知的标签解析）、
`inplace_backfill.py`（就地补标的骨架：对齐校验、UPSERT、事件幂等）。

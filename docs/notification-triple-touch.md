# 通知三次触达与幂等治理（1.2）

## 要解决的问题

1.1 的通知只有一条：「转写成功」。它发生在转写完成的瞬间，颗粒度太粗，文案也像是回显状态码，
不像说给人听的。一场会在群里安安静静——纪要写好了没人说，任务要确认了也没人提，任务闭环接不上。

问题拆开是两层：

- **颗粒度**：一场会其实有三个值得通知的时刻，只发第一个，后两个没人通知，用户得自己回工作台看。
- **文案**：「状态：minutes_generating」这种话，机器能看懂，人不爱看，看了也不知道下一步干什么。

1.2 把「一场会」的通知拆成三次触达，每条都回答三个问题：**发生了什么、要不要我动手、动手去哪**。

## 三次触达

一场会在群里的固定节奏是三条消息，按时间先后：

| 次序 | 通知 | 谁发 | 内容 | 要回答的问题 |
|---|---|---|---|---|
| ① | 转写完成 | relay 侧 | 录音已经变成文字 | 发生了什么 |
| ② | 纪要写好 | 工作台 `notify.py` | 这场会定了什么，直接摊在群里 | 要不要我动手 |
| ③ | 任务待确认 | 工作台 `notify.py` | 逐条确认 / 驳回 | 动手去哪 |

三条消息的次序是**语义上的先后**，靠发送顺序保证：纪要卡排在任务卡之前，任务卡排在任务抽取之后。
用户刚散会、在手机上看群，应该先知道「纪要好了、会上定了这几件事」，再看到「这几件要你确认」。

### ② 纪要写好卡

这条是 1.2 补上的中间一环。以前纪要生成完只在工作台里静默归档，群里没动静；用户往往隔很久才发现。

纪要卡不只报一句「纪要已生成」——那样还得回电脑翻。它把纪要压成手机一眼看得完的三块：

- **一句话摘要**：从纪要的摘要段取一段。
- **这场会定了哪几件事**：从决议段抽 3 条。
- **下一步**：告知接下来会抽任务、发确认卡，点确认才开工。

核心原则是**抽不到就留空，绝不拿别处的内容凑数**。纪要是老六段式模板就认「三、核心决议」，
是新模板就认「决议」下的有序列表；没有决议段就退回三级标题，但措辞从「定了」换成「聊了」——
议题是讨论对象，不是定论，不能用错词。

### ③ 任务待确认卡

1.1 已就绪，1.2 只把文案按三问重写，并确认它排在纪要卡之后。

## 完整链路

```
转写完成（relay 侧发「转写完成」）
  → 纪要生成（本地 Agent）
  → 工作台通知「纪要写好」：摘要 + 决议 + 下一步      ← 1.2 新增
  → 本地 LLM 抽取任务草稿
  → 工作台通知「任务待确认」：逐条确认 / 驳回          ← 1.1 已有，1.2 改文案
  → 用户在飞书逐条确认
  → 长连接回调 → 任务状态落库 → 卡片原地更新
```

## 通知幂等：kind + ref_key

通知会由后台扫描循环周期性地触发，同一件事可能被扫到很多次。**每条通知都落一张 `notifications`
台账，`kind + ref_key` 唯一，发过就不再发。** 通知发送失败只记日志、不重试排队，等下一轮扫描自然补发——
这是靠「扫描周期本身就是重试」来保证最终送达，而不是另建一套重试队列。

`ref_key` 怎么选，是这条机制的关键。它要精确到「同一件事的同一份内容」，多一点少一点都会出问题：

| kind | ref_key | 为什么这样选 |
|---|---|---|
| 转写完成 | 转写任务 id | 一次转写只报一次 |
| 纪要写好 | `minutes_version_id` | 同一份纪要只惊动一次；用户改纪要产生新版本才再发；重新抽取任务不重复打扰 |
| 任务待确认 | `extraction_id` | 同一抽取批次只推一次卡 |
| 停滞提醒 | `task_id:冷却桶` | 同一任务在同一个冷却窗口内只提醒一次 |
| 每日晨报 | 日期 | 一天一条 |

其中「纪要写好」用 `minutes_version_id` 尤其关键：纪要会被反复重新生成，如果按会议去重，第一次发过
之后就永远沉默了；按纪要版本去重，只有真正产生了新的纪要内容才再通知，重新抽取任务（没动纪要）不会打扰。

## 文案人话化

通知文案统一按三问写，机器术语一律翻译成人的说法：

- **时长**：`87 分钟` 写成 `1 小时 27 分钟`，不是回显毫秒数。
- **日期**：写成 `8 月 6 日`，不是 ISO 时间戳。
- **任务号**：只在失败通知里附，顺利时没人看编号。
- **状态**：relay 侧用一张状态文案表取代 `状态：minutes_generating` 式的回显；新状态没写文案时有保底句，
  不静默丢通知。

## 实战踩坑：驳回按钮一直点不动

1.1 上线后，任务确认卡上的「驳回」按钮从第一天起就没生效过，但「确认」一直是好的。排查发现根因极小：

回调监听进程调工作台 API 时，「确认」传了 `{}`（空对象），「驳回」没传 body。服务端的写接口统一
校验 `Content-Type: application/json`，没传 body 的请求不带这个头，直接被挡在 422/400 上；传了 `{}`
的请求带上 `Content-Type`，才放行。于是「确认」没事、「驳回」次次被拦。

修法一行：`reject()` 也传 `{}`。教训是**写接口的空 body 不等于「没有 body」**——客户端要么统一传
`{}`，要么服务端对缺省 body 做兼容，二者只留一个判断点，否则就会出现「同一个按钮组里有的好有的坏」
这种半死不活的状态。

## 前置条件

与 1.1 相同：一个带回调能力的飞书应用机器人、本机 lark-cli 凭证、`LARK_CHAT_ID` 指向目标群。
通知全部走同一条通道，`LARK_CHAT_ID` 留空则三次触达整体静默，任务确认退回工作台网页内完成，
转写、归档、纪要、任务看板不受影响。
